# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"ພະຈົນໄພຄວາມຮູ້ / Knowledge Quest": a 2D learning-adventure game built on the Phaser 4 + React + TypeScript + Vite template (`phaserjs/template-react-ts`). The player learns from a Textbook, crafts gear, explores a Stage for Materials, and returns to the Village Hub — the design lives in [docs/Game Design Doc-Village Hub.md](docs/Game%20Design%20Doc-Village%20Hub.md) (Lao). Read [CONTEXT.md](CONTEXT.md) for the glossary before naming anything: **Realm, Stage, Zone, Credit, Material, Textbook, Village Hub, Health, Durability, Portal block** — and avoid *level, score, coins, lives, game over*, which belong to the old platformer this game replaced. Hard rules: **Credit comes only from learning; Materials come from exploring, or from growing Seeds that exploring gave** (see [ADR 0005](docs/adr/0005-wallet-holds-credit-only.md) and [ADR 0007](docs/adr/0007-materials-can-be-grown-from-explored-seeds.md)).

The plan for growing the game to 100 Stages in 10 Realms (Phase 0–10, each with sub-targets) is [docs/plans/2026-10-29-hundred-stages-realms.md](docs/plans/2026-10-29-hundred-stages-realms.md). Phases 0–10 are done (the glossary, 100 numbered Stages on a 10×10 map, generated Stages with enemy scaling, lesson numbers, the question at the end of a Stage, the first-Stage tutorial, Durability with repairs, Armor, Potions, a 30-slot Backpack, Portal shards, blocks and the World Gate, Seeds with Saplings, the Garden and the Storage chest, Realm 2 with Stages 11–20, its Textbook pages 11–20, blue-ore gear and a Boss, and Realm 3 with Stages 21–30, Textbook 3 (Operating Systems), copper gear, End Task and a Boss). Realms 4–10 are content work: follow [docs/content-guide.md](docs/content-guide.md). The plan that aligned the code with the GDD is [docs/plans/2026-10-28-village-hub-alignment.md](docs/plans/2026-10-28-village-hub-alignment.md); each phase has a status note listing what is done and what was left over.

## Commands

```bash
npm install          # install dependencies
npm run dev-nolog    # dev server, no ping — prefer this one (npm run dev sends an anonymous template usage ping)
npm run build-nolog  # production build to dist/, no ping (npm run build pings)
npx tsc --noEmit -p tsconfig.json   # typecheck (no dedicated npm script exists)
npm run lint         # eslint .
npm run test         # domain/application unit tests once (Vitest)
npm run test:watch   # same, in watch mode
npm run test:e2e     # Playwright specs in e2e/ (starts the dev server itself)
```

`npm run lint` enforces the dependency rule: files in `domain/` and `application/` fail lint if they import `phaser`, `react`, `infrastructure/` (or, for domain, `application/`) or touch `window`/`localStorage`. Game rules belong in a use case, not in a modal or scene: the UI calls the use case and reacts to its result or event.

Vitest ([vitest.config.ts](vitest.config.ts)) picks up `src/domain/**/*.test.ts`, `src/application/**/*.test.ts` and the pure data-validator tests in `src/infrastructure/content/`; infrastructure is checked by typecheck, the Playwright specs and playing the game, see [docs/adr/0002-testing-strategy.md](docs/adr/0002-testing-strategy.md). `e2e/playthrough.spec.ts` is an opt-in experimental bot (`PLAYTHROUGH=1`) that plays with real keys; see its header for what it can and cannot do. Run e2e on its own — running it while `build` is going starves the CPU and makes specs flaky. [playwright.config.ts](playwright.config.ts) starts Chromium on the real GPU (software WebGL is too slow to run specs in parallel), warms the dev server once in `e2e/globalSetup.ts` and runs 3 workers (full run about 1 minute). On a machine without a GPU set `PW_NO_GPU=1` (1 worker, software rendering); `PW_WORKERS=n` overrides the count. Specs start with empty storage already, so do not `localStorage.clear()` + `reload()`.

The dev server's configured port is 8080 ([vite/config.dev.mjs](vite/config.dev.mjs)); Vite moves to the next free port if it is taken. [.claude/launch.json](.claude/launch.json) holds the preview config. Build config is split across `vite/config.dev.mjs` and `vite/config.prod.mjs`.

## Architecture

**Clean Architecture, 3 layers** — see [CONTEXT.md](CONTEXT.md) and [docs/adr/0001-clean-architecture-layering.md](docs/adr/0001-clean-architecture-layering.md).

- `src/domain/` — entities and rules, no Phaser/React/DOM imports, no x/y. `entities/` (Wallet, Backpack, Book, Quiz, Health, Boss, Enemy, EquipmentState, Skin, StageProgression, ResourceNode, EnemyAttackPlanner, HeldItem, SaveData, …), `ports/` (interfaces the outside world implements), `utils/` (e.g. `nextObjective`), and [DomainEvents.ts](src/domain/DomainEvents.ts), the framework-free emitter.
- `src/application/` — one use case per file (`PurchaseBookUseCase`, `SubmitBookExamUseCase`, `PerformAttackUseCase`, `HarvestResourceNodeUseCase`, `ReturnToVillageUseCase`, `AwardChapterClearUseCase`, …), each with a colocated `.test.ts`. They orchestrate entities, emit domain events (`player-died`, `boss-damaged`, `skin-changed`, …) and are called directly from infrastructure.
- `src/infrastructure/` — everything framework-specific:
  - `phaser/` — `main.ts` (game config), `scenes/` (`Preloader`, `TitleScene`, `Game`), `objects/` (Player, Enemy, Boss, NPC, Spike, platforms), `scenery/` (`VillageBuilder`, `StageBuilder`, `WorldBuilder`), `controllers/` (`CombatController`, `InteractionController`), `stages/StageDefinition.ts`, `effects/` (particles, floating text), `Level.ts` + `levelCatalog.ts` (only the names of the village and of a Stage number).
  - `react/` — `App.tsx`, `PhaserGame.tsx`, `components/` (HUD and the modals: Textbook, Academy, Workshop, Forge, Backpack, GateRepair, Waypoint, QuizFinisher, StageMap, Skin, Settings, `TitleMenu` (the full-screen start menu: CSS background art, keyboard and mouse list, Continue/New Game once there is progress), pause menu), `hooks/` (`useGameEvents` subscribes to game/domain events, `useGlobalShortcuts` for M/B/Esc/I, `useModalState` for every modal's open state and Esc-closes-the-top-one, `useSkinShop` (the Skin shop only opens in the village, from Mina's dialogue action `open-skin-shop`; the hero is frozen while it is open), `useDialogue`).
  - `composition.ts` creates the one live `entities` (a domain `GameState`) and the concrete `repositories` (localStorage ports); `saveSnapshot.ts` is a thin bridge from `entities` to the save use cases (`createCurrentSnapshot`, `autoSaveGame`, `restoreEntitiesFromSnapshot`, `resetEntitiesToNewGame`); `storage/` has `SaveManager` (3 slots + autosave, implements `SavePort`) and `safeStorage`; `audio/SoundManager`; `content/` loads and validates the game data.

**Two scenes of gameplay, one `Game` scene class.** [Preloader](src/infrastructure/phaser/scenes/Preloader.ts) loads assets and JSON, [TitleScene](src/infrastructure/phaser/scenes/TitleScene.ts) plays the title music and runs the start transition (the start screen itself is React's `TitleMenu`), and [Game](src/infrastructure/phaser/scenes/Game.ts) runs both the Village Hub and the Stage, chosen by `levelKey` (`village` or a Stage id `stage-001` … `stage-100`, see `domain/entities/StageNumber.ts`). Switching is done by restarting `Game` with a different `levelKey` (React emits `change-level`). A new scene must be added to the `scene: []` array in `main.ts`, and one that React needs to reach must emit `'current-scene-ready'` itself.

**React ↔ Phaser go through `EventBus`** ([infrastructure/EventBus.ts](src/infrastructure/EventBus.ts), a `Phaser.Events.EventEmitter`), not props. The scene opens modals with events (`open-library`, `open-academy`, `open-workshop`, `open-forge`, `open-gate-repair`, `open-waypoint`, `open-stage-map`, `open-quiz-finisher`, `start-dialogue`); React answers with `change-level`, `quiz-finisher-passed/failed`, `gate-repaired`, `dialogue-open-state`; the scene reports `stage-cleared`, `backpack-changed`, `weapon-changed`. `PhaserGame.tsx` forwards the live scene via the `currentActiveScene` prop and the `{ game, scene }` ref. This is separate from `DomainEvents`, which must not depend on `phaser`.

**Data-driven content, loaded once and checked.** Gameplay data is JSON, not code. [main.tsx](src/main.tsx) calls `loadGameContent()` ([infrastructure/content/ContentCatalog.ts](src/infrastructure/content/ContentCatalog.ts)) before rendering: it fetches `items`, `books`, `questions`, `recipes`, `enemies`, `realms`, `nodes` and `stages` from `public/data/`, validates each with a parser that names the file and path of any mistake (`items.json: items[3].maxStack must be a number`), and on failure shows an error page instead of a broken game. Screens and scenes then read `getGameContent()` synchronously — never `fetch` JSON yourself. `items.json` also fills `entities.itemCatalog` (the domain `ItemCatalog`), which is where stack sizes and "what is lost on death" come from (`story: true` items are kept); do not keep your own list of item ids in code. [ContentIntegrity.test.ts](src/domain/ContentIntegrity.test.ts) checks that the files reference each other correctly (recipe ingredients, drops, stage spawns, question pages), so run `npm run test` after editing any JSON. The reasoning, and what was deliberately not done (a schema library, React Context), is in [ADR 0006](docs/adr/0006-content-catalog-and-single-game-state.md).
- `public/data/realms.json` is the ten Realms (subject, portal colour, biome, Textbook, Portal items) and `public/data/nodes.json` the kinds of Resource node (label, texture, `reach`, tool, `strikes`, drops; see "Strike" in CONTEXT.md, the rule lives in `ResourceNode` and `harvestResourceNodeUseCase`).
- `public/data/stages.json` lists all 100 Stages in order. A built one (`status: "ready"`) names its `layout` (a level JSON) and its Zones, and everything in a Zone is an entry of `contents` told apart by `kind`: `node` (by `nodes.json` id, with optional `overrides` of `strikes`/`drops`), `enemy`, `miniboss` (only Stage 5 of a Realm), `boss` (only Stage 10), `sign`, `waypoint`, `gate` and `exit` (a Stage without a boss is cleared by walking past its `exit`). A Stage not built yet is `{ number, realm, status: "placeholder" }`: grey on the map, cannot be entered. [StageDefinition.ts](src/infrastructure/phaser/stages/StageDefinition.ts) holds its parser, which resolves the `contents` into the lists the scene builds from and checks the rules (100 in order, realm = ceil(number/10), an exit or a boss, known node ids).
- `public/data/player-animations.json` describes the player skin sheets: a 8×8 grid of 32×48 cells where each row is an animation (`idle run air attack tool wall hurt faint`: frames, fps, loop) and every frame has the hand anchor (fist x/y, angle, in front/behind, hidden). `Player` builds its Phaser animations from it and `HeldItemSprite` follows the anchors; each weapon/tool in `items.json` has a `held` grip (a drawn placeholder is used until `held.image` points at a PNG in `public/assets/held/`). The sheets and the anchors are generated by `python tools/art/build_player.py` (see `tools/art/README.md`), not edited by hand.
- `public/assets/levels/{village,stage-001,005,010,015,020,025,030}.json` (the generated Stages have no file) — world width, player spawn, platforms, spikes, moving platforms, `scenery` (`forest` or `cave`) and `arenaFromX` for a cave level that ends in a boss arena ([ADR 0003](docs/adr/0003-level-data-as-loaded-json.md)).
- Building a Stage means turning its `stages.json` entry from `placeholder` into `ready` + (if new) `nodes.json` and `enemies.json` ids. No code changes. A hand-made Stage (1, 5 and 10 of a Realm) names a level JSON in `public/assets/levels/stage-NNN.json` as its `layout`. An ordinary Stage sets `"layout": { "generate": { "biome": "forest"|"cave", "seed": N, "screens": 2-8 } }` and fills its Zone with a `spawn-pool` (`nodes`, `count`, `enemies`, `enemyCount`, optional `enemyType`/`patrolDistance`/`speed`) and an `exit` without an x; [StageGenerator.ts](src/infrastructure/content/StageGenerator.ts) builds the same level from the seed every time, and `scaling` at the top of `stages.json` makes ordinary enemies tougher the further the Stage is ([StageScaling.ts](src/domain/entities/StageScaling.ts)). In development `?stage=N` on the address opens Stages 1..N and starts Stage N, and `window.__entities` is the live game state for browser tests (do not `import()` `composition.ts` from a test: while the app is loading it can be a second copy). Balance numbers (prices, HP, drops) belong in the JSON and the GDD, not in scenes.

**Lessons and the question at the end of a Stage.** Every Textbook page has a `lesson` number `<stage>-<order>` (`3-1`) and every question the `lesson` of its page (`ContentIntegrity.test.ts` checks both). A built Stage lists `lessons` in `stages.json`; walking out of it freezes the scene and opens `StageQuestionModal` with one question drawn from those lessons (`pickStageQuestion`). `answerStageQuestionUseCase` pays `stageQuestion.credit` Credit for the first correct answer of that Stage (remembered in `StageProgression.questionRewardedStages`); a wrong answer still clears the Stage. A boss Stage keeps the Quiz Finisher; its question is drawn from the Textbook of the Stage's Realm (`realms.json` `bookId`, sent with the `open-quiz-finisher` event). Page numbers (`pageNumber`) stay as the reading-progress keys; book ids are still `book-ch1`/`book-ch2`.

**Durability.** `items.json` gives a weapon or tool `durability` (uses; no field = it never wears, like the wooden sword; such an item must have `maxStack` 1). Each Backpack slot keeps its own `durability` (missing = full, saved as an optional field), see `Backpack.getDurability` / `wearItem` / `restoreItem` and the rules in [Durability.ts](src/domain/entities/Durability.ts). `performAttackUseCase` (with the Backpack) and `harvestResourceNodeUseCase` wear the sword or tool by one per use and a Broken one does half damage / counts half a Strike; dying in a Stage that is not safe takes a tenth of every item's maximum (`returnToVillageUseCase`). `RepairItemUseCase` restores an item for the Materials in `public/data/repairs.json` (never Credit), from the Forge's Repair tab (swords) or the Workshop's (tools, so a worn axe never has to wait for the Forge to open); `RepairList` is the shared list. Events: `item-worn`, `item-broken`, `item-repaired`. Armor wears the same way in Phase 6.

**Portal shards, blocks and the World Gate.** Each Realm in `realms.json` names a `shardItem` and a `blockItem` (`story` Materials, never lost). A Mini-boss and a Boss drop shards from their drop table in `enemies.json` (the Boss's reward after the finisher question is that table too, every time); `portal-block-<colour>` is crafted at the Forge (5 shards + Materials) once the Realm's Textbook teaches it (`unlockedRecipes`). `placePortalBlockUseCase` (opened from the Portal gate section of the World Map, `StageMapModal`) uses the block of Realm N−1 to open Realm N for good (`entities.realms`, saved as `openedRealms`); the first Stage of Realm N opens at once if the Boss Stage before was cleared, otherwise clearing it opens it (`nextStageToUnlock`). Story Materials a Boss or Mini-boss drops into a full Backpack are not lost: `stashStoryOverflowUseCase` puts them in `entities.pendingRewards` (saved, `pendingRewards`) and `claimPendingRewardsUseCase` moves them in when there is room (App checks when the Backpack changes or closes). A tutorial step can wait for an event with `showAfter`. Icons are generated by `tools/art/build_portal_icons.py`.

**Seeds and Saplings.** `nodes.json` gives a plant `seed: { itemId, chance }` and `regrow` (`"on-enter"` or `{ minutes }`); `overrides.seed` in `stages.json` changes it for one node. `harvestResourceNodeUseCase(..., { random, clock, regrowth, stageId })` drops the Seed on the last Strike (best effort) and, for a plant with minutes, records the harvest time in `entities.plantRegrowth` (key = Stage id + node id, saved as `plantRegrowth`). The scene builds a harvested plant as a Sapling (frame 3 of its sheet, `[E]` prompt with the time left) until `Clock` says it is grown, then turns it back (`Game.growPlants`, twice a second). `Clock` and `Random` are domain ports (`SystemClock`, `MathRandom` in infrastructure); a development build moves time with `window.__advanceClock(ms)`. Seeds are plain Materials (halved on death); planting them is the Garden (Phase 9).

**Garden and Storage chest.** A Seed item has `plant: { minutes, harvest }` in `items.json`. `entities.garden` (`Garden`: 6 Plots, up to 12) holds what is planted and when; `plantSeedUseCase`, `harvestPlotUseCase` and `expandGardenUseCase` (Materials from `public/data/garden.json`, never Credit) work on it with a `Clock`. The Garden is a place you walk in: the Garden door of the Village Hub (E at x = 1010) emits `change-level` `garden`, which restarts `Game` with `levelKey` `garden` (`assets/levels/garden.json`, `GARDEN_LEVEL_KEY` in `levelCatalog.ts`, no entry in `stages.json`). [GardenBuilder.ts](src/infrastructure/phaser/scenery/GardenBuilder.ts) draws the Plots on the ground (x = 300, 400 …) and returns them as `InteractiveBuilding`s with live labels: E on an empty Plot emits `open-garden` (React's `GardenSeedPicker` asks which Seed), E on a ready Plot harvests, the sign at x = 1500 buys another Plot, the door at x = 60 goes home; the scene redraws the Plots in `growPlants`. `entities.storage` is the Storage chest: a `Backpack` built with 40 slots (`new Backpack(slots, catalog, maxSlots)`), moved to and from with `transferItemUseCase` in `StorageModal` (chest at x = 235); dying never touches it. Both are saved (`garden`, `storage`, additive).

**Build time.** A recipe in `recipes.json` may have `craftSeconds` (Game time; none = made at once, as potions and the repair kit are). `startCraftUseCase` takes the Materials and Credit and puts the job in `entities.crafting` (`CraftingQueue`, one job at a time, saved as `crafting`, additive); `Game.update` ticks it with the frame delta, so it only moves while the scene runs (not paused, not on the title screen, not closed); `collectCraftUseCase` hands the result over when it is done (`CraftingStatus` in the Workshop and Forge windows, a HUD badge, `data-testid` `crafting-*`). In the village a smith ([CraftingWorker.ts](src/infrastructure/phaser/objects/CraftingWorker.ts), sheet `npc_smith.png` from `tools/art/build_smith.py`) appears in front of the building that owns the running job (the recipe's `building`), hammers with sparks and shows a bar and the time left over his head, cheers when it is done and leaves when it is collected; `Game.update` feeds him the job. A spec that crafts a timed recipe finishes it with `entities.crafting.tick(ms)`.

**Dash.** `public/data/skills.json` `movement.dash` sets the Dash (speed, `durationMs`, `dodgeMs`, `cooldownMs`; `SkillCatalog.ts`). Shift or the touch button `virtual-dash` call `Game.tryDash` → `dashUseCase(entities.movement, …)` (cooldown; in the air it needs the `air-dash` ability, once per jump) → `Player.dash` (flat burst without gravity, the speed cap lifted, afterimages). While `Player.isDodging` nothing hurts the hero: `CombatController` asks `player.canBeHurt`. `entities.movement` (`MovementAbilities`) is saved as `movement` (additive; the Dash is always there). The skills plan is [docs/plans/2026-10-30-skills-and-tool-upgrades.md](docs/plans/2026-10-30-skills-and-tool-upgrades.md) (S1 done).

**Skills.** `public/data/skills.json` `active` lists the active Skills (`SkillCatalog.ts`: `realm`, `cooldownMs`, an `effect` with a `type` such as `wave`, a `concept` from the Textbook). `entities.skills` (`SkillProgression`: learned skills and the K/L slots, saved as `skills`, additive) and `entities.skillCooldowns` (not saved). A skill is learned when the exam of its Realm's Textbook is passed: `syncSkillsWithBooksUseCase` through `syncSkills()` in `infrastructure/skills.ts`, called after the exam, after loading a save (so an old save gets the skills of books it already passed) and at app start; a new skill goes on the first empty slot. K/L and the touch buttons (`virtual-skill`) call `SkillController.use(slot)` → `castSkillUseCase` (slot, cooldown) → the effect (`wave`: a piercing projectile, damage = sword damage × `damageMultiplier`, a Boss takes `bossShare` of it; it also destroys enemy projectiles). The Academy has a Skills tab (`SkillsPanel`), the HUD shows the slots with their cooldown (`readSkillSlots`). The `area` effect (End Task, Realm 3: a circle of `radiusPx` around the hero, everything inside is hurt and stunned, a Boss only hurt, no target in the circle = no cooldown) works like `chain`. The `chain` effect (Ping, Realm 2) finds the nearest enemy in front within `rangePx`, then the nearest to each one within `jumpRangePx` (up to `jumps`, a Boss can be one of them for `bossShare` of the damage and is never stunned), hurts each and `Enemy.stun(stunMs)`; with no target it says so and starts no cooldown. A stunned enemy (`entity.stun`, `isStunned`, counted down in `Enemy.update`) stands still, shows 💫 and does not hurt by touch (`CombatController` checks `enemy.isStunned`); `EnemyAttackBehavior.interrupt` cuts an attack short. **Ranks:** each skill has `upgrades` (2 entries: the cost in Credit and Materials of rank 2 and rank 3, with the new `cooldownMs` and the effect numbers that change). The parser resolves `rankCooldowns` and `effectByRank` (`effectAtRank(skill, rank)`); `entities.skills.rankOf(id)` is 1 to 3 (saved as `skills.ranks`, rank 1 is not stored); `upgradeSkillUseCase` (Academy Skills tab) takes Credit and Materials; `castSkillUseCase` starts the cooldown of the rank and `SkillController` casts the effect of the rank. **Movement unlocks:** `skills.json` `movement.unlocks` (`{ ability, afterBossStage }`); `syncMovement()` (`infrastructure/skills.ts`) gives the abilities whose Boss Stage is in `completedStages`, called after a clear (the Boss message tells), after loading a save and at app start; with `air-dash` the Dash works once per jump in the air. A new effect `type` needs its method in `SkillController` and an entry in the parser. Use `import { Math as PhaserMath } from 'phaser'` for runtime helpers: the global `Phaser` is only a type and is not defined when the code runs. Plan: [docs/plans/2026-10-30-skills-and-tool-upgrades.md](docs/plans/2026-10-30-skills-and-tool-upgrades.md) (S1 to S5 done; End Task, the area skill of Realm 3, is S6's first).

**Secret ledges.** `layout.generate.secret: true` in `stages.json` makes `StageGenerator` add a platform that only the air dash reaches (`secretPlatforms` in the `Level`, also in `platforms`; `generated.secret = { x, surfaceY }`): 72 px above a high step, `SECRET_GAPS` (200–230 px) from its edge, with no other high step within `SECRET_CLEARANCE` of it, added after every random draw so the rest of the layout is unchanged. The Zone must then have exactly one `{ "kind": "node", "node": "...", "secret": true, "overrides": {...} }`, which is placed on the ledge (`StageResourceNode.surfaceY`, `StageBuilder` draws a ✨ over it); the parser fails when the ledge does not fit (change the seed or `screens`). The jump numbers are in `physicsConstants.ts` (`maxLeapGap(rise, dashDistance)`); `LevelReachability.test.ts` checks that no plain jump reaches a ledge and a jump with the air dash does, for the real Stages and 500 seeds per biome. Stages 11–14 and 16–19 have one (Stage 13 is 4 screens so one fits); the hand-made Stages 15 and 20 do not.

**Tool tier.** A node's `toolTier` is enforced: a tool of a lower tier (`pickaxe-t1` on the tier 2 copper vein) is refused with `missing_tool` and `requiredTier` (`toolTierOf` reads the tier from the id), a higher tier is fine. Every node of Realms 1 and 2 is tier 1; the Realm 3 copper vein is tier 2 (the Pickaxe T2 comes from Realm 2's blue ore).

**Tool upgrades.** `recipes.json` has steps `{ targetToolId, targetLevel 1..3, building: "workshop", creditCost 0, strikeWeight, ingredients }` (axe and pickaxe T1 and T2; strike weights 1.5, 2, 3: a 3-Strike tree takes 3, 2, 2, then 1 Strike; the parser refuses Credit and a weight of 1 or less). `entities.toolUpgrades` (`ToolUpgrades`, +0..+3 by tool item id, saved as `toolUpgrades`, additive) is raised by `upgradeToolUseCase` (Materials only, the tool must be in the Backpack) from the Workshop's Upgrade tab (`ToolUpgradePanel`). `harvestResourceNodeUseCase` multiplies each Strike by `context.toolStrikeWeight(toolId)` (`toolStrikeWeight` reads the level and the recipe); `InteractionController` passes it in. Upgrades are instant (they do not use the build-time queue) and the hammer is not upgradable.

**Armor and Potions.** An `armor` item has `slot` (head/body/feet), `armorHearts`, optional `speedBonus` and a `durability`. Worn pieces live in `EquipmentState` (with their own Durability) and take no Backpack slot; `equipArmorUseCase` / `unequipArmorUseCase` move them and `syncArmorUseCase` makes `Health.maxArmor` match (a Broken piece gives none). `Health.takeDamage` spends Armor hearts first; `playerTakeDamageUseCase(health, armorContext)` also wears every worn piece; `Health.reset()` refills Armor hearts. A Potion is a `consumable`: the plain health potion uses `healAmount`, the others an `effect` (`strength`, `speed` for `durationSec`, `armor` for `amount` hearts). `drinkPotionUseCase` spends one; timed effects run in `entities.effects` (`ActiveEffects`, ticked by the scene, not saved) and are read by `performAttackUseCase` (damage) and the Player (`speedMultiplier`, with boots). **R** drinks the Quick slot (`entities.quickSlotItemId`, chosen in the Backpack); **Q** still swaps the sword. Recipe unlocks come from each book's `unlockedRecipes` (`recipeUnlocks.ts`). `armorContext` in composition.ts is what the Armor use cases take.

**Tutorial.** `public/data/tutorial.json` lists the hints of the first Stage in order, each with the `event` that finishes it (`moved`, `harvested:<node id>`, `enemy-defeated`, `backpack-opened`, `stage-cleared`, `book-fully-read`). `TutorialProgress` (`entities.tutorial`, saved as `tutorial: { done, dismissed }`) marks every step waiting for an event as done; code reports events with `notifyTutorial(event)` from [tutorial.ts](src/infrastructure/tutorial.ts), and the HUD shows the first step not done (with a ✕ to skip). A save from before the tutorial that already has progress reads as skipped. Stage 1 has `"safe": true`: dying there loses no Materials.

**Save data.** `SaveData.ts` defines the snapshot (`CURRENT_SAVE_VERSION = 7`); `migrateSaveSnapshot` sanitises anything loaded and starts older saves fresh, keeping only settings. Change the schema → bump the version and update `SaveData.test.ts`. The snapshot logic is in domain/application, not in React: `GameState.toSnapshot` / `loadFromSnapshot` and the use cases in `SaveSnapshotUseCases.ts` (create, restore, reset), tested with fake ports. Call `autoSaveGame()` after a change worth keeping rather than building a snapshot by hand: it writes at most every 3 seconds but postpones (never drops) a request that comes too soon, and saves the latest state when the page is hidden or closed. `GameState` members are created once and loaded **in place** — never assign over `entities.equipment`, `entities.books` and the like, or references held by scenes and screens go stale.

**Sprite–entity pairing.** Phaser objects that carry rules (Player, Enemy, Boss) hold a direct reference to their domain entity and pass it into use cases; geometry-only objects (platforms, spikes) have no entity. Keep movement/rendering inside the object's own `update()`; put rules (health, damage, drops, Credit) in `domain/`/`application/`.

**Gameplay constants.** Design resolution is 1280×720 with `Scale.FIT`; `WORLD_HEIGHT` in `Game.ts` must equal the config height in `main.ts`. Art is mostly placeholder shapes drawn with `Graphics` / generated textures plus the skin spritesheets in `public/assets/`.

**Phaser types vs. runtime imports.** Type-only references (`Phaser.Physics.Arcade.Body`, `Phaser.Scene`) can use the ambient global `Phaser` namespace; anything used at runtime (base classes, enums) must be a named import from `'phaser'` — there is no default export.
